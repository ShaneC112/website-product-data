# Sanity And Operator Workflows

Azure and Studio apply separate gates to different decisions. This distinction prevents internal pipeline quality scoring from becoming an opaque editorial publishing rule.

## Draft Ingestion And Publish

After composition, Azure invokes the shared bridge mapper and evaluates `evaluateBridgeEligibility`. A product that fails this internal gate is held in Azure and no Sanity document is created. A passing product is written as a deterministic Sanity draft, using the shared identity to avoid duplicate drafts from concurrent delivery.

Studio applies the independent `evaluateStudioPublishReadiness` gate to editor-visible, fixable content. Editors publish through normal Studio workflow only after that gate passes. Pipeline-only scores and blockers are not persisted as Studio publication fields.

## Editorial Preservation

Re-crawls preserve editor changes at the `(variantId, field)` level. Unrelated source updates can still apply, while a conflicting source change is presented for an editor to accept or retain. The bridge contract is a compatibility boundary: a Studio change that removes or changes an Azure-written guaranteed field must update the shared bridge schema and its Studio guard test.

## Registry Synchronization

The Data field registry is authoritative. Azure projects eligible code-managed definitions into Sanity, while UI exposes the dry-run and approved apply operation. Directly mapped fields are not duplicated as Feature or Specification choices. UI never receives a Sanity write token; it validates and forwards the request to Azure's authenticated endpoint.

## Operator Surfaces

UI reads shared Azure storage through Data schemas and exposes validation, review, matching, swatch, and recovery workflows. Its writes are validated server-side and sent to Azure-owned functions. Studio Blueprint functions send narrow action references to Azure queues; browser code never receives Azure storage credentials or Function keys.

## Operator Action Transport

An operator action starts as a Sanity write, never a direct browser call to Azure. Studio writes a request document - either an append-only entry on an existing product (`sanityActionRequests[]`) for actions that target content already in Sanity, or a dedicated top-level document (for example `styleCodeImportRequest`) when the action must create content that does not exist in Sanity yet. A Blueprint document-event handler validates that request against the shared contract and forwards only a minimal reference (the document ID and request ID) to the `sanity-actions` queue, using server-only credentials the browser never sees.

Azure's queue worker treats the Sanity request document as the authoritative source of truth: it reads the current request from Sanity rather than trusting a fat queue payload, resolves live source data as needed, does the work, and patches progress and results back onto that same Sanity document as it proceeds - `processing`, then terminal outcomes, with structured per-outcome results (for example excluded, failed, held, or draft-created rows) rather than a single terminal status string that would make a mixed outcome unreadable. A destructive action that removes its own request document (a rebuild) logs its terminal outcome instead of attempting a status patch against a document that no longer exists.

The import-by-style-code workflow is the reference example: Studio's `Import by Style Code` pane creates a top-level `styleCodeImportRequest` document; the existing `sanity-actions` Blueprint function forwards its reference to Azure; Azure resolves the live M2CRM style-code group, fans out one crawl per eligible source row, and patches bounded `progressMessages` plus structured `successResults`/`failureResults` back onto that request document as each row's crawl reaches a terminal outcome. See `website-product-enrichment-azure/src/operator-actions/sanity/import-style-code/README.md` for the full walkthrough.

The product `Requeue Product` action is the reference example for the append-only-entry pattern (an entry on a document that already exists): Studio's product action menu offers three operations, each an entry in `sanityActionRequests[]`. `Crawl & Update` (`action: 'crawl'`) re-resolves live M2CRM eligibility for the product's style code and force-enqueues one manual crawl per eligible source row, preserving the existing Sanity document and its per-field editorial history. `Recover pipeline stage` (`action: 'recover'`) resumes the recoverable-queues stage ledger from an operator-chosen checkpoint through the same `crawlRecoveryExecutor` the Nuxt/HTTP recovery API uses, touching no Sanity document state beyond the request's own status. `Delete & Rebuild` (`action: 'rebuild'`) is the one irreversible operation: Azure purges every durable Azure Table row and blob scoped to the style group (crawl pages and their captured artefacts, extract details, image-classify outcomes, compose output/group state, the publish-match ledger, the crawl-run summary, and any manually-attached group PDFs), deletes the Sanity product document (draft and published) in one transaction, then force-enqueues a fresh manual crawl per eligible M2CRM source exactly as if the product were new - none of the normal re-crawl field-level editorial preservation applies, because there is no longer a document to preserve fields on. Because the request document is deleted along with the product, its terminal outcome is only visible in Azure Functions logs and the `sanity-actions.ndjson` trace, not as a status patch on the (now-deleted) document. See `website-product-enrichment-azure/src/operator-actions/sanity/update-product/processUpdateProductAction.ts` (`processCrawlAction`/`processRebuildAction`), `website-product-enrichment-azure/src/operator-actions/sanity/recover-pipeline/processRecoverAction.ts`, and `crawlStyleGroupPurge.ts` for the exact purge scope.

`src/operator-actions/sanity/` is the canonical code-organization pattern for Sanity-triggered action code, not just documentation for these two examples: `sanityActions.ts` stays a thin dispatcher (parse the queue message, read and validate the stored request, resolve `styleCode`, patch `processing`/`failed` status) and delegates each action family's own work to its own subfolder - `import-style-code/`, `update-product/`, `recover-pipeline/` today. Each subfolder owns its process function(s), its own focused test file (using a fake Sanity client rather than mocking the `@sanity/client` module, where the function already takes an already-constructed client), and its own README describing its purpose, files, and caller contract. Cross-cutting Sanity read/patch plumbing used by more than one action family (`sanityClient`, `readProduct`, `actionPath`, `patchActionStatus`) lives in `sanity/helpers/` and must not be duplicated per folder. Add a new action to this structure, not as inline logic in `sanityActions.ts`.

Not every Sanity-triggered action uses the `sanity-actions` transport described above, and this folder's convention accommodates that: when an action deliberately needs its own request/run/ledger lifecycle that the single append-only `sanityActionRequests[]` entry does not fit, its Blueprint Function writes directly to its own dedicated Azure Storage queue(s) instead of forwarding a reference through `sanity-actions`/`sanityActionsWorker`. Studio's `Create Imagery` action is the reference example: its Blueprint Function writes directly to `sanity-image-prepare`/`sanity-image-generate` with their own queue URL and shared SAS token, and its entire implementation - ingress, both queue workers, status endpoint, and its own durable ledger - lives in `website-product-enrichment-azure/src/sanity-images/`, independent of the main 7-stage pipeline and of `sanityActionsWorker`. The current implementation snapshots one immutable `roomImageQueueJob` per run, sends only a minimal queue reference, defaults missing legacy `statementTone` values to `balanced`, preserves an explicit `none` tone as the compatibility branch, and keeps the intermediate structured design brief transient rather than persisting it as part of the Sanity or ledger contract. `operator-actions/sanity/image-generation/README.md` is a deliberate stub recording this: when a Sanity-triggered action's implementation is fully self-contained in a different top-level folder, its `operator-actions/sanity/` subfolder holds only a README pointing there - not a code stub for its own sake.
